## 0. Owner's working rules (must follow)

The project owner (Abu Sayed) builds this as a **live demo for a "Software Engineer — AI & Automation" job
interview at a private hospital in Dhaka**. Every feature must be really built, cleanly layered, secure, easy
for non-technical staff, and explainable in an interview.

1. **Language:** the owner writes in Bangla/Banglish. Reply to the owner in **Bangla** (simple words; technical
   terms may stay in English). Code, comments, commit messages and these guides stay in English.
2. **Work in phases** (7 phases, see §3). The owner sends one prompt per phase. Build **only** that phase;
   future menu items stay as placeholders.
3. **Before coding a phase:** read both guides, inspect the code, give a short plan. **If anything conflicts with
   existing code, ask the owner first.** Never delete or rewrite working code without explaining why.
4. **Commit after each step** with a conventional message (`feat: …`, `fix(frontend): …`, `docs: …`).
   **No assistant co-author lines or "generated by" text in commits or PRs** — nothing assistant-related on GitHub.
   (Some Phase 1–2 commits still carry such trailers; rewriting pushed history is the owner's decision.)
5. **At the end of every phase**, give the owner (in Bangla): every file created/changed with why; commands to
   run; a manual test checklist (which account, what to check); likely interview questions with short answers.
   Then update §18 (phase log) here and the matching part of the frontend guide.
6. **Two repositories, cloned side by side:** `backend/` → github.com/abusayeds/hospital_management_server and
   `frontend/` → github.com/abusayeds/hospital_management_frontend, in one parent folder, named exactly
   `backend` and `frontend` (`npm run shared:export` writes into `../frontend`). Commit and push in each repo
   separately. No root README / `docs/` / Docker files. **No Docker** at all.
7. **No assistant/agent files in git:** `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor/` are ignored. Project
   knowledge lives in these two README guides only.
8. **Secrets never in git.** `.env` / `.env.local` are ignored; `.env.example` files hold placeholders only.
   **Never commit API keys.**
9. **Naming:** product **Testolife**, hospital **Testolife Hospital** (Keraniganj, Dhaka), patient chat
   **"Testo Life Assistant"**. Printed documents say "Generated by Testolife" (prompts may say "CareFlow" — use Testolife).
10. **"AI" wording:** never on patient-facing screens (landing, chat, patient portal). Allowed on staff/doctor
    screens where it is a safety label, e.g. **"AI-generated — verify before use"**.
11. **AI never diagnoses or prescribes.** AI output is a draft for staff, never auto-saved into a record.
    **Never send patient identifiers to an AI provider** (no name, phone, NID, address, patient code — only age,
    gender and clinical content). Emergencies in the chat are handled by code, not AI.
12. **Medical records are never hard-deleted and never silently changed.** Closed visits are read-only;
    corrections are audited addenda. Soft delete (`basePlugin`) everywhere else.
13. **No fictional patients.** The seed creates staff accounts, doctors, catalogues, templates and the knowledge
    base only. Patients are registered by reception with real phone numbers (WhatsApp messages are real — there is no
    simulator). Never add made-up phone numbers to the database.
14. The owner develops on **Windows** (PowerShell / Git Bash, `core.autocrlf=true`). Keep commands cross-platform.

## 4. Setup on a new computer

Prerequisites: Node.js 22.12+ (24 recommended), npm, Git, a MongoDB Atlas connection string (replica set).

```bash
cd backend
npm install
cp .env.example .env        # fill it in (table below)
npm run pdf:setup           # downloads headless Chrome for prescription / lab report PDFs (once)
npm run seed                # master data + demo staff accounts + knowledge base (no patients)
npm run dev                 # http://localhost:5000  → GET /api/v1/health
```

Generate secrets:
```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"   # JWT_SECRET_KEY
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # ENCRYPTION_KEY (exactly 64 hex)
```
Keep `ENCRYPTION_KEY` the same on every machine that uses the same database — NIDs encrypted with one key cannot
be read with another. The server **refuses to start** if `.env` is invalid and lists every problem.

## 5. Architecture

```
request → pino-http → helmet → CORS(CLIENT_URL) → body limit → cookie-parser → sanitize (NoSQL)
        → verifyOrigin (CSRF) → rate limit → /api/v1 router
        → [authenticate() → requirePermission()] → validateRequest(zod) → controller → service → model
service → recordAudit() · emitToPermission/emitToRoom (live UI) · publish(domain event) after commit
errors anywhere → globalErrorHandler → { error: { code, message, details } }
```

**Business logic lives only in services.** Controllers translate HTTP ↔ service calls. Services are reused by
routes, the assistant's tools, event consumers, seeds and tests.

### Conventions

- **Success:** `{ success, statusCode, message, data, pagination? }` (`sendResponse`); pagination `{ page, limit, total, totalPages }`.
- **Error (the only shape):** `{ error: { code, message, details } }`. Codes include `VALIDATION_ERROR`
  (details = `[{ path, message }]`), `INVALID_ID`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`,
  `DUPLICATE_KEY`, `RATE_LIMITED`, auth codes, and Phase 4: `VISIT_OPEN`, `VISIT_CLOSED`, `ALLERGY_CONFLICT`,
  `FOUR_EYES_REQUIRED`, `AI_NOT_CONFIGURED`, `AI_UNAVAILABLE`, `AI_INVALID_OUTPUT`. Messages are written for staff.
- Assistant tools never throw: business errors come back to the model as `{ error }` for it to explain.
- `throw new AppError(status, message, code?, details?)`; wrap handlers in `catchAsync`.
- `basePlugin` on domain models (timestamps, `createdBy/updatedBy`, soft delete auto-filtered).
- Money in **poisha** (integer). Dates as `YYYY-MM-DD` in **Asia/Dhaka** (`todayInDhaka`, `addDays`, `ageOn`).
- Real-time: personal data only to permission/doctor rooms; the public queue board (no key) gets masked data only.
- Domain events: `publish()` **after** the database change committed; payloads carry ids and dates only.
- Windows: working files are CRLF; scripted multi-line replacements must normalise `\r\n` first.

## 6. Authentication (Phase 2)

httpOnly cookies `tl_access` (JWT 15 min), `tl_refresh` (opaque, rotated, hashed at rest, path `/api/v1/auth`),
`tl_session` (flag for the route guard). Every request re-checks session + user + role from the DB. Rotation with
reuse detection (revokes all sessions), lockout after 5 failures (15 min, `423`), forced password change for
temporary passwords, CSRF = sameSite=lax + CORS/JSON-only + `verifyOrigin`. Sockets authenticate from the cookie.
Frontend idle sign-out at 15 min.

## 7. Roles & permissions (RBAC)

Code checks **permissions, never role names**. `src/config/permissions.ts` is the only mapping; the frontend
gets a generated copy (`npm run shared:export`). A 403 always writes a `PERMISSION_DENIED` audit entry.

**Object-level rule for medical records** (`modules/clinical/emr-access.ts`): a doctor opens a patient's EMR only
if the patient has (had, or will have) a non-cancelled appointment with **that doctor**, unless the user holds
`emr:read_all` (assigned to nobody by default). Enforced in the API for visits, EMR history, vitals history, lab
history/results and the AI summary. Nurses may read vitals history only for patients in today's list.
Only the visit's own doctor may write it. Lab results reach doctors only after verification.

## 8. Audit log

`recordAudit({ req, action, entityType, entityId, before, after, meta })` — never throws, strips secret-looking
keys, append-only (model blocks updates/deletes). Actions: `LOGIN`, `LOGIN_FAILED`, `ACCOUNT_LOCKED`, `LOGOUT`,
`LOGOUT_ALL`, `TOKEN_REUSE_DETECTED`, `CREATE`, `UPDATE`, `DELETE`, `VIEW`, `ROLE_CHANGE`, `ACTIVATE`,
`DEACTIVATE`, `PASSWORD_CHANGE`, `PASSWORD_RESET`, `PERMISSION_DENIED`.

Clinical audit: every EMR read (`VIEW` on Patient/Visit/LabOrder/AiSummary, including PDF prints with
`meta.output`), visit create/update (only changed fields, before/after)/close, addenda (`VisitAddendum`),
allergy overrides (`meta.allergyOverride`), vitals create/update, every lab transition, four-eyes refusals
(`PERMISSION_DENIED`, `meta.reason: "four_eyes"`), AI summary generate/feedback.

Assistant audit: inbox VIEW of a conversation, take-over / staff reply / hand-back / resolve / tags / notes
(`entityType: "Conversation"`, `meta.event`), knowledge article create/update/publish/delete/re-index, WhatsApp test
message. Bookings made by the assistant go through the booking service and are audited there (source
`chatbot` / `whatsapp`).

## 9. Hospital core (Phase 3)

- **Master data** (`master_data:manage`): departments, doctors (title, degrees, fees in poisha, follow-up fee +
  validity, weekly sessions with slot length and capacity, leaves, room, linked user account), services,
  lab tests (parameters with units and normal ranges), medicines (brand/generic/strength/form; text index),
  hospital settings (single document; name/Bangla name, address, phones, hours, booking window, cancellation
  cut-off, TV notice, `labFourEyes`).
- **Patients:** `TL-` codes, name + Bangla name, gender, DOB (or estimated from age), BD phone (+880),
  allergies, chronic conditions, blood group, emergency contact; NID **encrypted** (AES-256-GCM, only last 4 shown);
  duplicate warning (same phone + similar name) with explicit override; instant search by code / phone prefix / name;
  basic vs full view by permission.
- **Scheduling & booking:** pure slot engine (`scheduling/slotEngine.ts`), booking in a transaction with
  per-doctor/date/session serials from counters; **partial unique indexes** (only while `holdsSlot`) make double
  booking impossible even with parallel requests. Status machine in `appointment.service.ts`
  (`ALLOWED_TRANSITIONS`): booked → checked_in → in_consultation → completed; cancelled / no_show; send back.
  Reschedule links old/new rows. One booking service for every channel.
- **Queue:** priority emergency > elderly > normal, then serial. Doctor "call next" / call specific / recall /
  send back in transactions. Public queue board (`/display/queue`, no key) lists every doctor with masked names; announcements via socket.

## 10. Clinical (Phase 4)

### 10.1 Vitals (nurse)
One `Vitals` per appointment, recorded while the patient waits (today + checked in / in consultation).
BMI and flags are computed on the server with `shared/clinical-rules.ts` — the same file the browser uses for
instant colours. Screening thresholds: BP ≥ 140/90 abnormal, ≥ 180/120 critical; SpO₂ < 94 abnormal, < 90
critical; temp ≥ 100.4 °F fever, ≥ 103 critical; pulse, RR, Asian BMI cut-offs, fasting/random sugar.
Edits allowed only while still waiting (audited before/after); after that the doctor owns the record.
Nurse worklist: `GET /vitals/worklist`.

### 10.2 Visits / EMR / prescriptions (doctor)
- `Visit` (one per appointment): complaints, HPI, past history, examination, provisional/final diagnosis,
  investigations (catalogue lab tests or free text), prescription items (catalogue snapshot: brand, generic,
  strength, form; dose pattern `1+0+1`, meal timing, days or "continue", auto Bangla + English instructions),
  advice (Bangla/English), follow-up, referral, allergy overrides, `aiSummaryUsed`, addenda.
- **Start** (`POST /appointments/:id/visit`) is idempotent and moves a waiting patient to "in consultation".
- **Autosave** (`PATCH /visits/:id`) — only the visit's doctor, only while open; audit keeps only changed fields.
- **Allergy check:** a medicine matching a recorded allergy (by name or drug family, e.g. Penicillin →
  Amoxicillin) is refused with `409 ALLERGY_CONFLICT` unless the request carries an override with a reason;
  overrides are stored on the visit and audited. **Duplicate generics** come back as a warning.
- **Close** (`POST /visits/:id/close`): needs a diagnosis; in ONE transaction it signs the visit (RX number,
  vitals snapshot), creates the lab order for catalogue investigations, and completes the appointment. Then:
  audit, sockets, events `appointment.completed {visitId}` and `visit.closed {followUpDate}`.
- **Closed = read-only** (`409 VISIT_CLOSED`); corrections via `POST /visits/:id/addenda` `{ text, reason }`.
- **Call next is blocked** (`409 VISIT_OPEN`) while the current patient's visit is open.
- **Templates:** private per doctor (`/visits/templates`); another doctor's template answers 404.
- **EMR history:** `GET /patients/:id/emr` (visits + vitals trend), `GET /visits/:id` — both VIEW-audited.

### 10.3 Printed prescription (PDF)
`GET /visits/:id/prescription.pdf` (closed visits only). Headless Chrome renders HTML with the embedded
**Hind Siliguri** font (Bangla conjuncts shape correctly — simple PDF libraries break them). A4, hospital header,
doctor, patient line, C/C, O/E (vitals), diagnosis, investigations, allergies, ℞ with Bangla instructions,
advice, follow-up, addenda, signature, footer "Generated by Testolife". The **QR** holds
`<number>.<HMAC signature>`; `GET /public/verify/:code` (rate limited, no login) answers genuine/not genuine
with number, date, issuer, masked patient name and age — never diagnosis, medicines or contact details.
`Cache-Control: no-store`; every print is audited. The browser is started once and reused.

### 10.4 Laboratory
`LabOrder` (`LAB-` number): **ordered → sample_collected → processing → awaiting_verification → ready →
delivered** (cancel until release; verifier can send back with a reason → processing). Order lines snapshot the
catalogue (name, code, sample type, price, parameters with ranges). Results are flagged on the server
(low/high/abnormal/critical; 2× upper or ½ lower limit = critical). Submitting with blanks is refused.
**Four-eyes:** verification by the same person who entered results → `403 FOUR_EYES_REQUIRED` + audit.
Doctors see values only after verification; live `lab:report_ready` to the doctor's room. Reception hands over
and prints (`lab_report:deliver`). Verified report PDF: `GET /lab-orders/:id/report.pdf` (QR resolver `LAB`).

### 10.5 AI visit summary (doctor, staff-only)
A short brief of the patient's **past** records (closed visits, vitals, verified lab results) shown in the
doctor's panel. See §12 for the AI layer. Cached per patient (`AiSummary`), marked **stale** by the event
consumers of `visit.closed` and `lab.report_ready`; a request with the same de-identified input hash reuses the
cache. Always labelled **"AI-generated — verify before use"**, never written into the record automatically
("Insert into notes" is an explicit doctor action that sets `aiSummaryUsed`). Thumbs up/down feedback. All audited.

## 12. AI layer (`src/ai`)

- **Provider abstraction:** features call `generateStructured({ prompt, input, schema })` only. `AiProvider`
  has one method `generate()`; `providers/gemini.ts` implements it with model fallbacks. A new vendor = one file.
  `setAiProvider()` swaps it (tests use a fake provider). `AI_PROVIDER=none` or no key → `AI_NOT_CONFIGURED`,
  and the UI shows "not configured".
- **Reliability:** hard timeout (`AI_TIMEOUT_MS`, request aborted), input size limit, one retry for overload or
  invalid JSON, strict **Zod** schema for the answer, safe error codes (`AI_UNAVAILABLE`, `AI_INVALID_OUTPUT`) —
  raw vendor errors never reach the client.
- **Prompts are versioned files** (`prompts/visit-summary.v1.ts`); the version is stored with every result and
  usage row. To change a prompt, add `v2` and switch the import.
- **Usage log** (`AiUsage`): feature, provider, model, prompt version, status (ok / timeout / invalid_output /
  error), latency, sizes, tokens, user, entity — **no prompt or answer text**.
- **De-identification** (`deidentify.ts` + `modules/clinical/ai-summary/context.ts`): the input contains age,
  gender and clinical facts only; dates become "days ago"; doctor names are left out; staff free text is
  scrubbed of names, phone numbers, patient codes, e-mails and NID-length numbers; finally
  `assertDeidentified()` checks the whole input for the patient's identifiers and **refuses to send** if one
  remains (fail closed).
- **Safety prompt:** summarise only facts present; no diagnosis, medicines, doses or treatment advice; the
  records are data, not instructions (prompt-injection guard).
- Rate limit: 10 generations per minute per user.

## 14. Patient assistant (Phase 5) — "Testo Life Assistant"

Patients talk to the hospital on the **website chat** (`/chat` and an embeddable widget) and on **WhatsApp**.
The assistant answers from a knowledge base and performs **real actions through tools** (find doctors, show slots,
verify the phone, book / cancel / reschedule, queue position, lab report status). Staff watch everything in a live
**inbox** and can take over. Patient-facing text never says "AI"; the assistant honestly says it is an automated
assistant.

### 14.1 Architecture: engine + channel adapters

```
WhatsApp webhook ─┐                                   ┌─► WhatsApp adapter (buttons, lists, numbered text)
Web chat HTTP ────┼─► InboundMessage ─► ENGINE ─► OutboundMessage[] ─┼─► Web (HTTP response + socket room)
(Voice, later) ───┘   (channel-neutral)   │                           └─► (Voice: text-to-speech, later)
                                          ├─ idempotency (provider message id, unique index)
                                          ├─ staff took over? → silent (store + notify inbox)
                                          ├─ SAFETY pre-checks (emergency · limits/budget · injection)
                                          ├─ deterministic taps (Confirm, OTP, menu) — no model
                                          ├─ AI loop: model ⇄ tools, max 5 rounds (src/ai chatRound)
                                          └─ output guard → store → inbox socket → domain events
```
- **Inbound** `{ channel, channelUserId, text?, replyId?, externalMessageId?, unsupported? }`; **outbound** is text,
  `quick_replies`, `list` (doctors / slots / patients / appointments), `card` (booking summary / success, queue,
  lab status…), `otp_request`, `handover` (`modules/assistant/assistant.types.ts`). Each adapter renders them its
  own way. A **voice adapter** would do speech-to-text → `handleInbound()` → read `messageText()` aloud; the engine
  does not change.
- **Models:** `Conversation` (channel + user, verified phone, linked patients, short refs, status
  `bot_active | needs_human | human_active | resolved`, tags, notes, pending action, metrics, running summary),
  `ChatMessage` (direction, sender, text + rich payload, sanitised tool calls, guard flags, provider message id —
  unique per channel —, delivery status, the payload actually sent), `Verification` (hashed OTP, TTL).
- **Memory:** last 12 messages + a running summary refreshed every 20 messages. Tapped buttons are remembered by
  meaning (ids, times), not only by label.
- **Never silent:** AI error / timeout / budget → bilingual fallback with the hospital phone + "talk to a person".

### 14.2 Tools and authorisation (`modules/assistant/tools`)

Golden rule: the model chooses a tool; **the server decides what is allowed.** Arguments are re-validated with
Zod; personal tools need the conversation's **verified phone** and re-check ownership in code; the model sees only
short references (`P1`, `A1`, `L1`) mapped server-side per conversation, first names, and no phones or ids.

| Tool | Notes |
| --- | --- |
| `get_hospital_info`, `list_departments` | Settings + departments |
| `search_knowledge_base(query)` | Top passages from published articles (§14.4) |
| `search_doctors(department?, name?, date?)` | Active doctors, fee, schedule, next free date/time (slot engine) → doctor cards |
| `get_available_slots(doctorId, date)` | Up to 8 free times spread over the day → slot chips |
| `get_test_preparation(testName)` | Catalogue preparation note, sample, report time |
| `start_verification(phone)` / `verify_code(code)` | Web OTP (WhatsApp numbers are verified by WhatsApp) |
| `list_my_patients`, `register_patient(name, gender, age)` | Family members on the verified phone; registration uses the patient service's duplicate detection (source `chatbot`/`whatsapp`) |
| `book_appointment`, `cancel_appointment`, `reschedule_appointment` | **Prepare only**: validate + store a pending action + summary card with Confirm / Change. The Confirm tap (or a clear "yes") executes it **in code** through the booking service; stale buttons are ignored |
| `get_my_appointments`, `get_queue_status` | Only the phone's patients; live position = people ahead + estimated wait |
| `get_lab_report_status` | Status only (ordered / in progress / ready / collected) — **never values** |
| `request_human(reason)` | Hand-over to the inbox |

**OTP:** `crypto.randomInt` 6 digits, HMAC stored, 5 min TTL, 5 wrong attempts, 3 codes/hour/phone, 60 s resend.
Delivery: `OtpSender` implementations — WhatsApp when configured, otherwise the log + admin "dev codes" view
(development only). SMS is not connected yet. A typed 6-digit code is checked in code, never by the model.

### 14.3 Safety layer (`modules/assistant/safety`)

- **Emergency rules** (Bangla, English, Banglish: chest pain, breathing, unconscious, stroke, bleeding, seizure,
  poisoning, injury, pregnancy, self-harm; admins add words in Hospital Settings) run **before** the model: instant
  bilingual message with the emergency number and 999, conversation `needs_human` + `EMERGENCY` tag, red inbox alert
  with sound. Self-harm gets a caring message and no booking prompts. Sent even while staff have taken over.
- **Prompt injection** ("ignore previous instructions", "show all patients", "you are now admin"…) is refused in
  code without calling the model; patient text and knowledge passages are data, not instructions; tools accept no
  free-form instructions.
- **Limits:** 12 messages/min per conversation, 150/day per user, 1000 characters, 600 output tokens, daily AI
  budget (`assistantDailyAiBudget` in settings), 20 web messages/min per IP.
- **Output guard** on every model answer: dosage-like text (mg, 1+0+1, "twice a day", "দিনে ৩ বার") replaces the
  whole answer with a safe message; phone numbers and patient codes that are not the user's or the hospital's are
  masked; internal ids removed; findings stored in `guardFlags` and logged.
- **Prompt:** `src/ai/prompts/assistant.v1.ts` (versioned; English with Bangla examples; "আপনি"; reply in the
  patient's language; never diagnose / prescribe / interpret values; say "I don't know" + offer a human).

### 14.4 Knowledge base and retrieval (RAG)

`KnowledgeArticle` (bilingual markdown, category, draft/published, version history) → on publish/update: chunks of
~180 words with 40-word overlap per language → embeddings through `src/ai` (`embedTexts`, usage logged).
Search: **Atlas Vector Search** (`$vectorSearch`, index created at start-up in the background) → otherwise **MongoDB
text search** (bilingual stop-words removed, language "none" so Bangla is not stemmed) → otherwise keyword match.
Only published articles are searchable. Doctors, fees, schedules and slots are **never** answered from articles —
always from tools. Admin page: `/admin/knowledge` (editor, preview, publish, history, re-index, **Test the
assistant** = passages with scores + a preview answer on a throw-away conversation with side-effect tools disabled).

### 14.5 Web chat and widget

`/chat` (public, mobile-first): Bangla/English toggle, disclaimer with the emergency number, rich cards (doctor
cards, slot chips, confirm cards, big-serial success card with add-to-calendar, queue progress, lab status, OTP box),
typing indicator, retry. Identity = anonymous random id in an httpOnly cookie `tl_chat` (SameSite=None+Secure in
production for the widget). Staff replies arrive on socket room `webchat:<id>`.
**Widget:** `<script src="https://<frontend>/widget.js" async></script>` adds a floating button + an iframe of
`/chat?embed=1` (the website never touches patient data).

### 14.6 WhatsApp Cloud API

- **Security:** POST requires `X-Hub-Signature-256` = HMAC-SHA256(app secret, **raw body**) — the raw body parser is
  mounted only on `/api/v1/webhooks/whatsapp`; the NoSQL sanitiser strips dotted query keys, so the GET check reads
  `hub.*` from the raw URL. Invalid → 401.
- **Reliability:** answer 200 at once, process in the background; message ids are unique → Meta's retries never
  double-reply or double-book; send retries with exponential backoff on network/429/5xx; delivery statuses
  (sent/delivered/read/failed) update the messages; incoming messages are marked read.
- **Limits:** ≤3 reply buttons (title ≤20), lists ≤10 rows (title ≤24, description ≤72), body ≤1024 — otherwise
  numbered text ("reply 2"), remembered per conversation. Media → polite "text only" + human option.
- **24-hour window:** free-form messages only within 24 h of the patient's last message (bot replies always are;
  staff replies outside it are refused with a clear message). Template messages = Phase 6.

**Setup step by step**
1. developers.facebook.com → My Apps → Create app (type *Business*) → add the **WhatsApp** product.
2. WhatsApp → API Setup: note the test **Phone number ID**; add your own number under "To" recipients (test
   numbers can only message verified recipients).
3. Create a **permanent access token**: Business Settings → System users → add → generate token with
   `whatsapp_business_messaging` (the API Setup token expires in 24 h).
4. App settings → Basic → **App secret**.
5. `backend/.env`: `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_APP_SECRET`, and any random
   `WHATSAPP_VERIFY_TOKEN`. Restart.
6. Local development needs a public HTTPS URL: `ngrok http 5000` or `cloudflared tunnel --url http://localhost:5000`.
7. WhatsApp → Configuration → Webhook: callback URL `https://<tunnel>/api/v1/webhooks/whatsapp` (Admin → Channels
   shows it), verify token = `WHATSAPP_VERIFY_TOKEN` → Verify and save → subscribe to **messages**.
8. Send "hi" from your phone to the test number; watch Admin → Inbox. Admin → Channels → "send test message".

### 14.7 Staff inbox (`inbox:manage`: reception, super admin)

Three panes, live over sockets: list (Needs human, Emergency, Human active, Bot active, Resolved, All; channel;
search; emergencies pinned red; unread counts) · transcript (patient / assistant / staff / system, "Assistant checked
…" tool chips, safety flags, delivery status) · context (verified phone, patients on the phone → profile link,
upcoming appointments, tags, internal notes). Actions: **Take over** (assistant silent), reply (canned replies;
delivered through the patient's channel), **Hand back**, **Resolve** — all audited. Header bell: live count, beep
(three for emergencies), toast. A patient waiting in a taken-over chat longer than
`assistantTakeoverReminderMinutes` (settings) triggers one more alert.

### 14.8 Evaluation

`npm run eval:chatbot` — 32 scenarios (Bangla, English, Banglish) played through the real engine on an in-memory
database: expected / forbidden tools, forbidden content (doses, lab values), required content, hand-over, emergency,
"model not called", and database checks (real appointment with source `whatsapp`/`chatbot`, nothing booked or
cancelled without Confirm). Default = deterministic intent-router mock (`scripts/eval/mock-model.ts`, also run by
Jest in CI); `-- --real` evaluates the configured model. Scenarios: `scripts/eval/scenarios.ts`.

## 15. Automation engine (Phase 6)

Reminders, follow-ups, no-show offers, report-ready messages and staff alerts — driven by domain events and
schedules, sent through **one Message Outbox**. Code: `src/modules/automation/`.

### 15.1 How it works

```
domain event ─┐                         ┌─ guards: rule on? precondition still true? preferences,
              ├─► rule planner / event ─► AutomationJob ─► dispatcher (lease) ─┤  quiet hours, limits, duplicate
cron planner ─┘   handler (idempotent)    (scheduled)       every minute       └─► render template ─► Outbox ─► WhatsApp → SMS
```

- **Rule** (`rules/*.rules.ts`, contract in `rules/types.ts`): key, category, defaults, config schema, `events`
  and/or `plan` (which jobs SHOULD exist), `prepare` (at SEND time: re-check preconditions, collect variables),
  `postSend` (e.g. `appointment.lastReminderSentAt`). Rules register themselves; `modules/automation/index.ts` wires
  their event handlers to the bus (consumer name `automation:<rule>`).
- **AutomationJob** (`models/job.model.ts`): one planned send. Unique index **(ruleKey, dedupeKey)** → planning twice
  or receiving an event twice never creates a second job. Lifecycle:
  `scheduled → ready → sending → sent | failed`, or `cancelled` (precondition failed, opt-out, rule off, admin) /
  `superseded` (appointment rescheduled — `supersededBy` links the new job). Deferred jobs go back to `scheduled`
  with a later time (`deferCount`). Every outcome is in `decisions[]` with a **reason**: `sent`, `optOut`,
  `quietHours`, `rateLimit`, `budgetExceeded`, `preconditionFailed`, `duplicateSuppressed`, `ruleDisabled`,
  `superseded`, `manual`, `sendFailed`; every channel try is in `sendAttempts[]`.
- **Dedupe keys:** `apt:<id>:confirm`, `apt:<id>:T-1d`, `apt:<id>:T-90m`, `apt:<id>:no-show`, `apt:<id>:absence:<from>`,
  `fup:<visitId>:D-3`, `lab:<id>:ready`, `lab:<id>:sample`, `chat:<id>:<waitStart>:staff|patient`,
  `chat:<id>:idle:<lastInbound>`, `chat:<id>:emergency:<hour>`, `failures:<hour>`, `digest:<date>`, `bday:<patient>:<year>`.
- **Scheduler** (`scheduler.ts`, node-cron, started by `server.ts`, never in tests): every minute the dispatcher
  sends due jobs, then planners whose cadence matches run (1, 15, 60 min). At start-up every planner runs once.
  **Lease:** a job is claimed with one atomic `findOneAndUpdate` (ready → sending + `{workerId, until}`), so two
  processes can never send the same job; an expired lease (crashed worker) is recovered; shutdown releases leases.
  Jobs due right now (a confirmation) are dispatched immediately instead of waiting for the tick.
- **AutomationRun** (`models/run.model.ts`, kept 30 days): planner / event / dispatch runs with counts and errors.

### 15.2 Rules

Every rule's config also has `quietHoursOverride`, `dailyLimit`, `channels` (WhatsApp → SMS) and `templateKey`.
Admin changes are stored in `AutomationRuleSetting` (only values that differ from the code defaults).

### 15.3 Message Outbox (single source of truth)

`OutboxMessage` = every outgoing message: automation (`source: automation`), chatbot replies (`chatbot`), staff
inbox replies (`staff`), system notices, in-app staff alerts (`channel: inapp`), admin test sends (`test`), and
verification codes (stored **masked**). Fields: patient, toType/toRef, channel, messageKind (`session` / `template`
/ `sms` / `inapp`), templateKey + version, variables, **renderedText** (exact text), buttons, status
(`queued → sending → sent → delivered → read` | `failed` | `cancelled`), providerMessageId, `deliveryUpdates[]`,
related entity, ruleKey/job, conversation/chatMessage, `replyWindowClosesAt`, `repliedAt`/`replyAction`,
`cost` (reserved for Phase 7).
- `outbox/outbox.service.ts` is the only way automation reaches a patient: WhatsApp inside the **24-hour window** →
  session message with reply buttons (`auto|<action>|<id>`); outside → the approved **template** (name, language,
  `{{1}}…` parameters, quick-reply payloads); no template or a Meta error → **SMS fallback** (`outbox/sms.ts`:
  `SmsProvider` interface + stub that only logs; plug a gateway with `setSmsProvider()`).
- The automated message is also stored in the patient's WhatsApp **conversation** (`sender: automation`), so a reply
  lands in the same chat the assistant knows.
- Phase 5 senders were wrapped: the WhatsApp and web adapters, the web chat route, the OTP sender and the admin
  test message all write Outbox rows (`outbox/record.ts`); WhatsApp delivery webhooks update both `ChatMessage` and
  `OutboxMessage` (statuses only move forward).

### 15.4 Templates

`MessageTemplate`: key, category, channels, declared **variables** (name, type `string|date|time|number|money|url`,
required, sample), bodies `{bn, en}`, buttons `{action, label{bn,en}}` (≤ 3, ≤ 20 chars), `whatsappTemplateName`,
`whatsappLanguages`, `whatsappParams` (variables for `{{1}}, {{2}}…`), `isActive`, `version` + `history` (rollback
creates a new version). Engine `templates/render.ts`: only `{{name}}`, no code; **validated on save** (unknown
placeholder, bad syntax, bad WhatsApp mapping, button limits); values are plain text (braces stripped, capped);
dates/times localised; Bangla digits per `messageNumerals`; a line whose optional values are empty is dropped.
Defaults for every rule in `templates/defaults.ts` (inserted once at start-up / seed, never overwriting edits).
Messages carry first names, doctor, date, time, serial, room — **never** results, diagnoses, medicines or anyone
else's details.

### 15.5 Responsible messaging (checked right before every patient send)

1. Rule enabled, automation not paused. 2. `prepare()` — precondition still true. 3. **Preferences**
(`Patient.preferences`): category switches `reminders` / `followUps` / `labReports`; `optOutAll` (STOP) silences all
except **essential** rules; `marketing` is opt-in and never after STOP. 4. **Quiet hours** (`quietHoursStart` /
`End`, default 21:00–09:00 Dhaka) → deferred to the morning unless the job is urgent AND the rule allows override.
5. **Limits** → deferred to tomorrow morning, never dropped: per-rule `dailyLimit`, global `automationDailyBudget`,
per-phone `perPhoneDailyCap` (reminder-style rules). 6. **Duplicate**: identical text to the same phone within
`dedupeWindowMinutes` (30) → skipped.

### 15.6 Replies (`replies.ts`)

An interaction handler runs before the model. Buttons `auto|confirm|<appointmentId>` etc., or a typed answer
("Cancel", "বাতিল", "2") to the last automated message within 48 h:
- **confirm** → `appointment.confirmedByPatient` (ownership checked against the verified phone), thank-you reply;
- **reschedule** → the same doctor's free times (`get_available_slots` tool) → `reschedule_appointment` tool →
  summary + Confirm → existing reschedule service;
- **cancel** → `cancel_appointment` tool → Confirm → existing cancel service → "New time" button;
- **rebook / book** → free times of the right doctor → normal booking flow; **queue** → `get_queue_status` tool;
- **stop** / typed **STOP** → `optOutAll` for every patient on that phone (audited) + confirmation with how to opt
  back in; **START** → back on. Free text continues in the assistant. WhatsApp retries are ignored (message id).

### 15.7 Real WhatsApp only, and the preview tool

There is **no simulation**: every patient message goes to Meta for real (owner decision, 2026-10-01). Automated
tests replace the transport (`setWhatsAppTransport`, `tests/fake-whatsapp.ts`) so they never reach a phone.
Set the four `WHATSAPP_*` variables (§14.6) and restart. Meta's free **test number** delivers only to recipients
added in the Meta dashboard (API Setup → To, max 5); a business number after Meta verification reaches everyone.
Outside the 24 h window a message needs an approved template (`tl_appointment_confirmation` … with the same
parameter order); otherwise the SMS fallback is tried — **no SMS gateway is connected yet**, so that attempt is
recorded as failed ("No SMS gateway connected yet"); connect one with `setSmsProvider()`.
**Preview world** (`POST /automation/preview-world`, admin): replays planners hourly up to a time in the next 24 h,
plus queued jobs, and shows who would get what and whether it would send, defer or skip — nothing stored or sent.

### 15.8 Data

`npm run seed` creates no patients. To test, register yourself in Reception with your own WhatsApp number (the
number must also be in Meta's recipient list while using the test number), book, and watch the messages arrive.
On 2026-10-01 all earlier fictional patients and their appointments, visits, lab orders, chats, messages, jobs and

### 15.9 Adding a rule

1. Add a template to `templates/defaults.ts` (bn + en, variables, buttons, WhatsApp mapping).
2. Create the rule with `registerRule({...})` in `rules/<area>.rules.ts` (import it in `rules/index.ts`): choose a

   everything and returns only safe variables, optional `postSend`.
3. Planner + postSend tests in `tests/api/automation-rules.test.ts`. New event? See §11.
